# docs/ について

このフォルダは、リポジトリの**内部構造・データフロー・API仕様**を、人にもAI(Claude Code等)
にも同じ精度で伝えるための資料集。

## ルートの README.md との役割分担

- **ルートの `README.md`** — 「何ができるアプリか」「画面をどう操作するか」「ディレクトリに
  何が置いてあるか」という利用者/開発者向けの機能仕様。まずこちらを読む。
- **`docs/` 配下** — README には書かれていない「内部でどう繋がっているか」を扱う。
  修正依頼(バグ修正・機能追加・仕様変更)を出すときに、影響範囲を特定するための資料。

## 中のドキュメント

| ファイル | 内容 | こんな時に読む |
|---|---|---|
| [architecture.md](./architecture.md) | 画面遷移とデータの流れ、共有状態(`VideoProject`)、非同期ジョブ+ポーリングの共通パターン、ファイル配信の注意点 | 「どの画面のどの状態を触ると何に影響するか」を知りたい時 |
| [api-reference.md](./api-reference.md) | `src/app/api/` 配下の全エンドポイントのリクエスト/レスポンス一覧表 | API の挙動を変える・新しい API を足す時 |
| [glossary.md](./glossary.md) | UI上の日本語表現とコード上の識別子(型名・変数名)の対応表 | 「"テロップの出現演出"を直したい」のようにUI用語で依頼が来た時、該当コードを特定する |

## 修正依頼の出し方(推奨)

このドキュメントをAIに読ませたうえで依頼する場合、次を伝えると精度が上がる:

1. **どの画面か**(例: `/edit` のクリップ編集タブ、`/create/style` の参考画像アップロード)
2. **UI上でどう見えているか**(ボタンのラベル、表示文言など) — [glossary.md](./glossary.md) で
   コード上の名称に変換できる
3. **現状の挙動と期待する挙動の差分**

例:「`/edit` の音声タブで、AIナレーション生成が失敗した時にエラーメッセージが出ずに
無反応に見える。生成失敗時もトーストでエラーを表示してほしい」

## メンテナンス方針

このフォルダはコードの実体(ディレクトリ構成・関数名・スキーマ)を都度参照する形で書いており、
コピーではなく要約・関係整理が目的。**大きな構造変更(状態の持ち方、ジョブ方式の変更、
API の追加/削除)をしたら、該当ドキュメントも合わせて更新する。**
